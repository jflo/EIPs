## Abstract

This EIP specifies a distributed key generation (DKG) facility for the consensus layer. Each period, a committee of `DKG_COMMITTEE_SIZE` validators is sampled from the registered validator set and jointly generates a BLS12-381 keypair whose secret exists only as threshold shares: no party ever holds it, and any `RECONSTRUCTION_THRESHOLD` committee members can jointly exercise it while fewer learn nothing. Dealings are committed with KZG polynomial commitments verified against the [EIP-4844](./eip-4844.md) structured reference string, so no new trusted setup is required. All adjudication-relevant messages — dealings, complaints, justifications, and public shares — are beacon block operations, making the qualified dealer set and the resulting group public key objective consensus data. The facility exposes a threshold-decryption interface to consumer protocols; [EIP-8184](./eip-8184.md) (LUCID) is the motivating consumer.

## Motivation

Several protocol designs require a party that can be trusted to *reveal a secret at the right time*: encrypted mempools ([EIP-8184](./eip-8184.md)), commit-reveal schemes, and randomness designs all reduce to this. Assigning that duty to a single party concentrates non-reveal risk, bribery exposure, and censorship surface on one identifiable actor. Replacing the single party with a threshold committee converts "one party's discretion" into "a coalition of hundreds," with defection publicly attributable.

Prior committee-based designs either secret-share per message (ciphertext size linear in committee size) or require a DKG whose dealing traffic is quadratic and whose dispute handling is left informal. This EIP specifies the DKG as a first-class consensus protocol, because it is one: it has phases, deadlines, an on-chain state machine, failure modes, and validator duties. Consensus-layer implementers should encounter it as a peer of the sync committee and attestation machinery — with its interactive dispute-resolution round (the *complaint round*) fully specified — rather than as a rationale sketch inside a consumer EIP.

Design goals:

* **No new trusted setup.** Dealing commitments and share proofs verify against the public EIP-4844 KZG setup already embedded in every client. Only the public setup elements are consumed; the ceremony secret `τ` is never used or referenced.
* **Objective adjudication.** Whether a dealer is qualified, and what the period's public key is, must be derivable from chain data alone.
* **Bounded, explicit failure.** A stalled or failed key generation degrades to a specified fallback, never to an ambiguous state.
* **Consumer neutrality.** The facility exposes a generic threshold keypair and decryption interface; it does not know about mempools.

## Specification

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT", and "MAY" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### Constants and parameters

DKG_COMMITTEE_SIZE                  = uint64(512)

# Phase schedule, in epochs before the start of the period being generated.

### Cryptographic preliminaries

All group elements are BLS12-381 points in compressed form: G1 as `Bytes48`, G2 elements only as consumed from the EIP-4844 setup. All points arriving from the network MUST pass subgroup checks.

Committee polynomials have degree `RECONSTRUCTION_THRESHOLD - 1 = 319` over the BLS12-381 scalar field. Seat `j` (for `j` in `[0, DKG_COMMITTEE_SIZE)`) is assigned the evaluation point `ω^j`, where `ω` is a fixed primitive `DKG_COMMITTEE_SIZE`-th root of unity. Note that blob verification uses a 4096-point domain at degree 4095; this EIP uses the same proof system and setup at a 512-point domain and degree 319 — the same techniques (including FK20 batch opening) apply, but not the blob code paths as-is. The evaluation point `0` is not an element of the domain and is used only for deriving the group public key by interpolation.

Two KZG checks are used:

1. **Scalar-valued opening** — `verify_kzg_proof(commitment, z, y, proof)` exactly as defined in the Deneb specification of [`verify_kzg_proof()`](https://github.com/ethereum/consensus-specs/blob/86fb82b221474cc89387fa6436806507b3849d88/specs/deneb/polynomial-commitments.md#verify_kzg_proof).
2. **Group-valued opening** — `verify_kzg_proof_g1(commitment, z, Y, proof)`, the standard variant in which the claimed evaluation is supplied as a G1 point `Y = [y]` rather than a scalar (as used in aggregatable DKG constructions; see Rationale). Validity condition, with `[1]₂` and `[τ]₂` taken from the EIP-4844 setup:

```
e(commitment - Y, [1]₂) == e(proof, [τ]₂ - z·[1]₂)
```

Both checks consume only public setup elements. Only `[τ]₂` from the G2 side of the setup is required, which the published EIP-4844 setup provides.

### Participation keys

Validators register a dedicated encryption key. The participation key is distinct from the validator signing key and is used only to receive encrypted dealing shares.

```python
class DKGKeyRegistration(Container):
    validator_index: ValidatorIndex
    participation_pubkey: Bytes48   # BLS12-381 G1

class SignedDKGKeyRegistration(Container):
    message: DKGKeyRegistration
    signature: BLSSignature          # validator signing key, DOMAIN_DKG_COMMITTEE
```

Registrations are beacon block operations. A registration is valid if the validator is active, the pubkey passes a subgroup check, and any prior registration for the index is at least `EPOCHS_PER_DKG_PERIOD` old (rate-limiting key rotation). A validator is **eligible** for committee selection in period `p` if its registration was included at least `EPOCHS_PER_DKG_PERIOD` before the selection epoch for `p`, preventing last-moment adaptive registration. Whether registration should instead be replaced by a key derived from the validator's existing identity — making all validators eligible — is an open question; see Security Considerations.

### Committee selection

At the selection epoch for period `p+1` (i.e., `DKG_LOOKAHEAD_EPOCHS` before the period starts):

```python
def get_dkg_committee(state: BeaconState, period: uint64) -> Vector[ValidatorIndex, DKG_COMMITTEE_SIZE]:
    seed = get_seed(state, dkg_selection_epoch(period), DOMAIN_DKG_COMMITTEE)
    eligible = get_eligible_dkg_indices(state, period)
    return compute_committee_by_shuffling(eligible, seed, DKG_COMMITTEE_SIZE)
```

Selection uses the existing swap-or-not shuffle. Seats are indexed `0..DKG_COMMITTEE_SIZE-1` in shuffled order. The committee is public from the selection epoch onward; the lookahead is the minimum required to complete dealing, and deliberately no longer (see Security Considerations on bribery lead time).

### Phase 1: Dealing

Each seated member `i` samples a uniformly random polynomial `f_i` of degree `RECONSTRUCTION_THRESHOLD - 1` and:

1. Broadcasts and submits for inclusion a signed dealing:

```python
class DKGDealing(Container):
    period: uint64
    dealer_seat: uint16
    polynomial_commitment: KZGCommitment   # commits to f_i

class SignedDKGDealing(Container):
    message: DKGDealing
    signature: BLSSignature                # DOMAIN_DKG_DEALING
```

2. Sends each other seat `j` its evaluation, encrypted to seat `j`'s participation key:

```python
class DKGShare(Container):
    period: uint64
    dealer_seat: uint16
    recipient_seat: uint16
    encrypted_share: ByteVector[144]   # ECIES to participation_pubkey: 48B ephemeral G1 || AEAD(32B f_i(ω^j) || 48B KZG proof) || 16B tag
```

Dealings MUST be included in beacon blocks during the dealing window (`MAX_DKG_DEALINGS_PER_BLOCK` per block); at most one dealing per `(period, dealer_seat)` is valid, and a second conflicting signed dealing for the same seat and period is attributable equivocation. Shares are **never** included in blocks: they propagate on per-recipient-seat gossip topics (analogous to attestation subnets) to which only the recipient subscribes. Dealers SHOULD compute the `DKG_COMMITTEE_SIZE - 1` share proofs with FK20 batch opening.

On receipt, each recipient decrypts its shares and verifies each against the dealer's on-chain commitment with the scalar-valued check at its own evaluation point. Recipients MAY verify optimistically in aggregate — one check of the summed shares and summed proofs against the summed commitments — falling back to per-dealer checks only on failure, to attribute blame.

### Phase 2: Complaints

A seat that received an invalid share, or no share, from an on-chain dealer submits during the complaint window:

```python
class DKGComplaint(Container):
    period: uint64
    complainer_seat: uint16
    dealer_seat: uint16

class SignedDKGComplaint(Container):
    message: DKGComplaint
    signature: BLSSignature   # DOMAIN_DKG_COMPLAINT
```

Complaints are beacon block operations. At most one complaint per `(period, complainer_seat, dealer_seat)` is valid. Note that non-delivery is not provable; the complaint mechanism does not distinguish "sent garbage" from "sent nothing" — both are answered the same way.

### Phase 3: Justifications

An accused dealer MUST answer every on-chain complaint during the justification window by revealing, in the clear, the exact share owed to the complainer:

```python
class DKGJustification(Container):
    period: uint64
    dealer_seat: uint16
    complainer_seat: uint16
    share: Bytes32     # f_i(ω^j), revealed
    proof: KZGProof

class SignedDKGJustification(Container):
    message: DKGJustification
    signature: BLSSignature   # DOMAIN_DKG_JUSTIFICATION
```

Justifications are beacon block operations, verified in the state transition with the scalar-valued KZG check against the dealer's commitment. Revealing one evaluation of a degree-319 polynomial discloses nothing about `f_i(0)`; the complainer's share simply loses confidentiality, and the complainer MUST use the revealed value as its share from dealer `i`.

**Disqualification.** After the justification window closes, dealer `i` is disqualified if any on-chain complaint against it lacks a valid on-chain justification, or if complaints against it were filed by `RECONSTRUCTION_THRESHOLD` or more distinct seats (under the corruption bound, such a complaint mass cannot be mustered by corrupt seats alone). The **qualified set** `QUAL` is the set of seats with a valid on-chain dealing, minus disqualified dealers — computable by every node from chain data alone. If `|QUAL| < RECONSTRUCTION_THRESHOLD`, key generation for the period has failed (see Failure handling); this bound also guarantees, under the corruption assumption, that `QUAL` contains at least one honest dealer, whose contribution keeps the group secret unknown to any coalition below threshold.

### Phase 4: Public shares and finalization

The group polynomial is `f = Σ_{i ∈ QUAL} f_i`, and seat `j`'s secret share is `sk_j = Σ_{i ∈ QUAL} f_i(ω^j)`, the sum of its verified received (or justified) shares. Because KZG commitments and proofs for a common evaluation point are additive, seat `j` also holds an aggregated proof `π_j = Σ_{i ∈ QUAL} proof_ij`. During the share publication window, each seat submits:

```python
class DKGPublicShare(Container):
    period: uint64
    seat: uint16
    public_share: Bytes48   # Y_j = [sk_j]
    proof: KZGProof         # π_j, aggregated over QUAL

class SignedDKGPublicShare(Container):
    message: DKGPublicShare
    signature: BLSSignature   # DOMAIN_DKG_PUBLIC_SHARE
```

verified in the state transition with the group-valued check against `C = Σ_{i ∈ QUAL} polynomial_commitment_i`:

```
verify_kzg_proof_g1(C, ω^j, Y_j, π_j)
```

**Finalization.** At the finalization epoch (`DKG_FINALIZATION_LEAD_EPOCHS` before period start), if at least `RECONSTRUCTION_THRESHOLD` valid public shares are on chain, the group public key is fixed as the Lagrange interpolation at `0` of the valid public shares from the `RECONSTRUCTION_THRESHOLD` lowest-numbered publishing seats:

```
PK_period = Σ_j λ_j · Y_j        # λ_j: Lagrange coefficients at 0 for the chosen seat set
```

Any valid subset yields the same point, since every verified `Y_j` lies on the polynomial fixed by `C`; the lowest-seats rule merely makes the computation canonical. `PK_period`, `QUAL`, the dealing commitments, and the verified public shares are recorded in beacon state. Requiring `RECONSTRUCTION_THRESHOLD` public shares before activation doubles as a liveness rehearsal: a committee that cannot finalize could not have decrypted anything either.

### Using the key: threshold decryption interface

Consumers encrypt with a KEM against `PK_period`: choose random `r`, set `U = [r]`, derive a wrapping key from `r·PK_period` (with a consumer-specific KDF context), and AEAD-wrap the payload key. To decrypt, seat `j` publishes:

```python
class DKGPartialDecryption(Container):
    period: uint64
    context_root: Bytes32     # consumer-defined; identifies what is being decrypted and under what trigger
    seat: uint16
    kem_value: Bytes48        # U
    value: Bytes48            # sk_j · U
    dleq_c: Bytes32           # Chaum-Pedersen DLEQ proof binding value to (Y_j, U)
    dleq_z: Bytes32

class SignedDKGPartialDecryption(Container):
    message: DKGPartialDecryption
    signature: BLSSignature   # DOMAIN_DKG_PARTIAL_DECRYPTION
```

The DLEQ proof shows `log_G(Y_j) == log_U(value)` entirely in G1: with fresh `k`, `T1 = [k]`, `T2 = k·U`, `c = H(domain || Y_j || U || value || T1 || T2)`, `z = k + c·sk_j`; verifiers recompute `T1 = [z] - c·Y_j`, `T2 = z·U - c·value` and check the hash. Verification of partials matters only for attribution and rewards: correctness of the combined result is checked by the consumer against its own binding commitment (e.g. LUCID's `key_commitment`), so partial verification sits off any attester critical path.

Given `RECONSTRUCTION_THRESHOLD` valid partials for the same `(context_root, kem_value)`, anyone computes the shared secret by Lagrange interpolation in the group — `Σ_j λ_j · value_j` — and unwraps the payload. Combining is permissionless; the first valid combination wins, so no combiner can withhold.

Partial decryptions propagate on a committee-scoped subnet, not by global flood. Consumers flood only the combined (constant-size) result.

Seats MUST securely delete their secret shares `DKG_SHARE_RETENTION_EPOCHS` after their period ends. Retained shares silently extend the compromise window of everything encrypted to that period.

### Failure handling

If finalization fails — `|QUAL| < RECONSTRUCTION_THRESHOLD`, or fewer than `RECONSTRUCTION_THRESHOLD` valid public shares by the finalization epoch — then:

1. The previous period's key, committee, and shares remain in service for the new period (**extension**). Members retain shares accordingly; the compromise window explicitly widens.
2. Dealing for the following period proceeds as normal.
3. After `MAX_CONSECUTIVE_EXTENSIONS` consecutive extensions, the facility enters **halted** status for subsequent periods until a dealing succeeds. Consumers MUST define behavior under halt (LUCID senders, for example, fall back to baseline `schemeID`s: a chosen key publisher or self-decryption).

Status (`ACTIVE` / `EXTENDED` / `HALTED`), the serving period, and its key are beacon state, so consumer behavior under degradation is objective.

### Duties, rewards, and penalties

Dealing, justification, and public-share duties are discharged by inclusion in blocks, so performance is objectively measurable in the state transition. Seated validators receive a per-period participation reward for (a) an included dealing that survives qualification and (b) an included valid public share; absence of either accrues an inactivity-style penalty of the same order. Magnitudes are TBD pending economic analysis, sized to make lazy non-participation irrational rather than to deter bribery (see Security Considerations). Partial-decryption incentives are consumer-defined (e.g. LUCID's `key_reveal_fee` and `participation_bits`).

Attributable equivocation — two conflicting signed dealings or public shares for the same `(period, seat)` — SHOULD be made slashable; the slashing condition and inclusion evidence format are open questions for the consensus-specs integration.

### Gossip topics

| Topic | Payload | Scope |
|---|---|---|
| `dkg_dealing` | `SignedDKGDealing` | global |
| `dkg_share_{subnet}` | `DKGShare` | per-recipient-seat subnets |
| `dkg_complaint` | `SignedDKGComplaint` | global |
| `dkg_justification` | `SignedDKGJustification` | global |
| `dkg_public_share` | `SignedDKGPublicShare` | global |
| `dkg_partial_decryption` | `SignedDKGPartialDecryption` | committee-scoped subnet |

All topics apply stateless validation before propagation: signature under the correct domain, period current-or-next, seat consistent with the selected committee, subgroup checks on all points, and per-seat rate limits.

## Rationale

### Why a standalone EIP

The DKG is a consensus protocol with phases, deadlines, block operations, state, and failure modes — the same species of object as attestations or sync committees. Embedding it as a rationale subsection of a consumer EIP understates its implementation surface and denies client teams a stable, independently reviewable specification. Factoring it out also decouples review risk: the consumer (LUCID) can evolve without re-litigating the DKG, and future consumers can adopt it without inheriting mempool semantics.

### Why KZG dealing against the EIP-4844 setup

A Feldman-style dealing publishes `RECONSTRUCTION_THRESHOLD` per-coefficient commitments per dealer — with 512 dealers, ≈8.4 MB of broadcast data that every node must download and verify each rotation. Committing to the dealing polynomial with a single KZG commitment collapses broadcast data to ≈72 KB per rotation; per-recipient proofs travel point-to-point inside already-encrypted shares. Summed across the committee the two variants move comparable total bytes (each KZG share embeds a 48-byte proof; Feldman shares verify against the broadcast vector), but per *node*, dealing drops from ≈8.4 MB to ≈140 KB, and verification drops from a 320-term multi-scalar multiplication per share to two pairings per share — with a further ~512× reduction available via optimistic aggregate verification.

The trusted setup this requires is exactly the one Ethereum already carries for blobs. Only public setup elements are consumed — the dealing checks need G1 powers far below the 4096 available and only `[τ]₂` from G2 — and the ceremony secret `τ` is never referenced. By contrast, recent "silent setup" threshold-encryption constructions, which eliminate the dealing round entirely, require powers of τ *in both groups up to committee size*, which the published EIP-4844 setup does not contain (65 G2 points), and carry ≈8× larger ciphertexts and ≈10× more expensive reconstruction. That trade was evaluated and declined for now; its unique advantages (un-stallable setup, per-ciphertext thresholds) are noted for future revisitation.

A known caveat of Pedersen-style DKGs applies: a rushing adversary can bias the distribution of the resulting public key (Gennaro, Jarecki, Krawczyk and Rabin, "Secure Distributed Key Generation for Discrete-Log Based Cryptosystems", 1999). The bias is tolerable for KEM-style threshold decryption of the kind specified here, but any future consumer using the key for other primitives must re-examine this. The group-valued opening variant follows aggregatable DKG constructions (Gurkan, Jovanovic, Kokoris-Kogias, Nikolaenko and Tomescu, "Aggregatable Distributed Key Generation", 2021).

### Why the public key is interpolated from public shares

Dealers could instead publish their contribution `[f_i(0)]` with a point-0 opening, and `PK_period` would be their sum. That requires a second proof mechanism and a second verification path. Since verified per-seat public shares `Y_j` are needed anyway — partial decryptions cannot be attributed or rewarded without them, and bare KZG commitments do not expose evaluations publicly the way Feldman coefficient vectors do — deriving `PK_period` by interpolating the `Y_j` reuses one mechanism for both purposes and shrinks the dealing message to a single commitment.

### Why complaints are on-chain

The complaint round is the DKG's dispute-resolution phase, made necessary by private share delivery: only the recipient can detect a bad share, creating a one-witness dispute. Off-chain complaint handling makes `QUAL` — and therefore the group key itself — a matter of local observation. Placing complaints and justifications in blocks makes disqualification a deterministic function of chain data, at negligible cost in the honest case (zero complaints). The justification-by-reveal design is safe because one evaluation of a degree-319 polynomial carries no information about the constant term, and the revealed dot was already owed to the complainer.

The alternative that eliminates complaints entirely — publicly verifiable encrypted shares (PVSS-style, as in the aggregatable DKG cited above) — converts all pairwise share traffic into broadcast traffic, forfeiting the per-node bandwidth advantage that motivates KZG dealing. It remains the natural upgrade path if the complaint machinery proves troublesome in practice, and this EIP's message layout is compatible with adding a proof-of-correct-encryption to `DKGShare` later.

### Threshold choice

`RECONSTRUCTION_THRESHOLD` sets two coalition scales in tension: `t` corrupt seats can decrypt everything encrypted to the period (confidentiality), while `n − t + 1` absent seats block all decryption (liveness). For n = 512 (binomial model, σ ≈ 10):

| `t` | Corrupt seats to break confidentiality | Faults tolerated for liveness | Confidentiality margin at 1/3 corrupt | Liveness margin at 25% faults |
|---|---|---|---|---|
| 342 (2/3) | 342 | 170 | ~16σ | ~4.3σ |
| **320 (5/8)** | **320** | **192** | **~14σ** | **~6.5σ** |
| 257 (1/2+1) | 257 | 255 | ~8σ | ~13σ |

At `t = 342`, liveness tolerance (170) equals the *expected* fault count if a third of seats are faulty — zero margin. `t = 320` trades confidentiality margin that was astronomically overprovisioned (~16σ → ~14σ) for a liveness margin that was dangerously thin (~4.3σ → ~6.5σ). The value is provisional pending game-theoretic review; the table, not the number, is the normative content of this choice.

### Committee size and period

512 is not inherited from `PTC_SIZE`; it falls out of two constraints. The corruption tail at the chosen threshold must be negligible against the assumed global corruption bound (satisfied with enormous margin at n = 512, and improving with n, since margins grow ~n while σ grows ~√n), while dealing cost grows as O(n²) in pairwise shares, bounding n above. 512 sits comfortably between; the Security Considerations note why the failure mode argues against economizing on committee size.

`EPOCHS_PER_DKG_PERIOD = 256` matches the sync committee, amortizing dealing cost (~140 KB per node per period is negligible even hourly) while bounding the per-period blast radius and bribery window to ~27 hours. Consumers with stricter blast-radius requirements can motivate shortening it; the schedule constants are the only coupling.

### Relationship to EIP-8184

LUCID's Key Reveal Committee section is the motivating consumer and is expected to be refactored into a profile of this EIP: `context_root` binds to LUCID's scheduling commitment, the reveal trigger and `key_reveal_fee` / `participation_bits` incentives remain LUCID-side, and combined outputs surface as ordinary `LucidKeyMessage`s whose validity is checked, unchanged, against `key_commitment`.

## Backwards Compatibility

This EIP requires a consensus-layer hard fork: new beacon block operations, beacon state fields (committee, `QUAL`, dealing commitments, public shares, group key, and status per active period — on the order of 100 KB), gossip topics, and validator duties. It introduces no execution-layer changes and no changes to existing transaction types. Validators that never register a participation key are unaffected except for the (open) question of default eligibility.

## Security Considerations

* **Two coalition scales, stated plainly.** `n − t + 1 = 193` seats suffice to withhold all decryption — attributable by omission against the signed partials of publishing seats — while `t = 320` seats suffice to decrypt everything encrypted to the period, *silently, before any consumer-defined trigger, leaving no onchain trace*. The confidentiality failure is undetectable; this is the strongest argument for a large committee and for consumers to state this trust honestly to their users.
* **Sampling assumes broad eligibility.** Committee statistics concentrate toward the global corruption ratio only if the eligible pool approximates the validator set. Opt-in registration lets an adversary over-register a sparse pool and dominate it regardless of committee size. Mitigations: derived (default) participation keys, registration aging (specified), and monitoring of pool participation. The corruption bound MUST be interpreted relative to the eligible pool.
* **Lookahead is bribery lead time.** The committee is public `DKG_LOOKAHEAD_EPOCHS` before its period begins — necessarily, since dealing takes time. The schedule sets the lookahead to the minimum the phases require.
* **Harvest-now-decrypt-later.** The KEM offers no post-quantum confidentiality: recorded `U` and `PK_period` decrypt retroactively once the discrete log falls. Rotation bounds the *forward* exposure window (bribery, share theft), not cryptanalytic exposure. Consumers whose plaintexts become public anyway (as in LUCID at reveal) lose little; consumers whose ciphertexts may remain forever-unrevealed inherit a real long-term exposure.
* **τ-leak exposure.** A party knowing the setup secret `τ` and acting as a dealer could forge openings for inconsistent shares; the damage (partials that fail to interpolate) manifests at decryption time for keys generated by dealing rounds conducted while `τ` was known. Keys from earlier rounds remain sound. Domain separation lives in message signing domains; the pairing checks themselves are unauthenticated algebra.
* **Complaint griefing.** Corrupt seats can force a dealer to justify — publishing dots of its polynomial. Under the corruption bound (< `t` corrupt), corrupt complainers can extract at most `t − 1` dots beyond what they already hold, which is exactly the leakage Shamir tolerates by construction. Honest complaints (real faults, partitions) add public dots; the margin between corruption bound and threshold absorbs realistic volumes. Complaint rate limits bound the block-space cost.
* **Share custody is the primary attack surface.** 512 known machines hold shares for ~27 hours; stealing `t` share files at leisure breaks the period silently. Encrypted-at-rest custody, deletion at retention expiry (specified), and shortened periods are the mitigations; DVT-style sub-splitting of individual shares is compatible and encouraged.
* **Extension widens exposure.** Each failure-driven extension prolongs one committee's custody and one key's blast radius; `MAX_CONSECUTIVE_EXTENSIONS` caps this before forcing an explicit halt, which consumers must handle.
